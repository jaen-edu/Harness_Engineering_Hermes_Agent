# 4교시: TASK 분해 Skill 설계 — task-breakdown
**시간**: 14:00–15:00 | **유형**: 설계 + 체이닝 실습

---

## 학습 목표

이 교시가 끝나면 수강생은:
1. "원자적 TASK(Atomic Task)"의 정의 기준 3가지를 말할 수 있습니다.
2. `task-breakdown` Skill을 설계하고 PRD와 체이닝할 수 있습니다.
3. 생성된 `TASK.md`의 품질을 스스로 검증할 수 있습니다.

---

## 1. TASK 분해의 중요성

### PRD만 있으면 AI는 어디서 시작할지 모릅니다

```
PRD: "사용자는 할 일을 추가, 조회, 완료, 삭제할 수 있어야 한다."

AI의 고민:
- 파일을 먼저 만들어야 하나? 클래스를 만들어야 하나?
- 테스트는 어디서부터? API부터? DB부터?
- 완료 기준은 무엇인가?
```

### TASK 분해 후

```
T01: Todo 항목 추가 (add 명령어)  → 완료 조건: test_add 통과
T02: Todo 목록 조회 (list 명령어) → 완료 조건: test_list 통과
T03: Todo 완료 표시 (done 명령어) → 완료 조건: test_done 통과
T04: Todo 삭제 (delete 명령어)    → 완료 조건: test_delete 통과
```

AI에게 T01만 넘기면 명확한 입력·출력·완료 기준으로 독립 실행 가능합니다.

## 2. 원자적 TASK의 기준

> **원자적 TASK(Atomic Task)**  
> 더 이상 쪼갤 수 없는 최소 단위의 개발 작업입니다.  
> 반대 개념: 에픽(Epic)은 여러 Task가 묶인 큰 단위입니다.  
> AI에게 에픽을 주면 결과물이 예측 불가능해집니다.

### 원자성 판단 기준 3가지

| 기준 | 질문 | 통과 예시 | 실패 예시 |
|------|------|----------|----------|
| **단일 책임** | 이 TASK는 한 가지만 하는가? | "add 명령어 구현" | "CRUD 전체 구현" |
| **테스트 가능성** | 완료를 테스트로 증명할 수 있는가? | `test_add_todo` 1개 | "사용자 경험 개선" |
| **독립적 완료** | 다른 TASK 없이 완료 가능한가? | 인터페이스 먼저 정의 | "T03이 완료되어야 가능" |

### 크기 기준

- **너무 작은 TASK**: 변수명 변경 하나 (TASK로 관리할 가치 없음)
- **적절한 TASK**: 함수 1–3개, 테스트 2–5개, 30분~2시간
- **너무 큰 TASK**: "인증 시스템 전체 구현" (다시 분해 필요)

## 3. task-breakdown Skill 설계

### TASK.md 출력 형식 설계

```markdown
# TASK.md: [프로젝트 이름]

## 요약
- 총 TASK 수: N개
- High 우선순위: X개
- 예상 총 소요시간: Y시간

## TASK 목록

| ID  | 우선순위 | 제목                | 의존  | 예상시간 |
|-----|---------|---------------------|-------|---------|
| T01 | High    | Todo 항목 추가      | 없음  | 1h      |
| T02 | High    | Todo 목록 조회      | 없음  | 30m     |

## 상세 TASK

### T01: Todo 항목 추가
- **완료 조건**:
  - [ ] `add("할 일 내용")` 호출 시 목록에 추가됨
  - [ ] 빈 문자열 입력 시 ValueError 발생
- **예상 테스트**: test_add_todo, test_add_empty_raises
- **의존**: 없음
```

### 설계 결정 사항

| 결정 | 이유 |
|------|------|
| 완료 조건을 체크박스로 | tdd-red Skill이 체크박스를 테스트 케이스로 변환 |
| 예상 테스트명 명시 | AI가 테스트 파일명을 일관되게 생성 |
| 의존 관계 명시 | 병렬 실행 가능한 TASK 파악 |

## 4. Skills 체이닝: prd-writer → task-breakdown

### 체이닝이란?

> **Skills 체이닝(Skill Chaining)**  
> 한 Skill의 출력이 다음 Skill의 입력으로 연결되는 파이프라인 구조입니다.  
> Unix 파이프(`|`)와 유사한 개념으로, 각 Skill은 입력 형식과 출력 형식을 명확히 정의해야 합니다.

```
PRD.md ──→ [task-breakdown Skill] ──→ TASK.md ──→ [tdd-red Skill] ──→ test_*.py
```

### 체이닝 시 주의사항

1. **파일명 고정**: 앞 Skill의 출력 파일명을 뒤 Skill이 알아야 합니다.
2. **형식 일관성**: 마크다운 테이블/섹션 구조가 일관해야 파싱 가능합니다.
3. **컨텍스트 전달**: Agent Mode에서 두 파일을 모두 컨텍스트에 포함합니다.

---

## 5. 실습: 3교시 PRD → TASK.md 자동 생성

1. 3교시에서 생성한 `PRD.md`가 있는지 확인
2. Agent Mode에서:

```
task-breakdown Skill을 사용해서 PRD.md를 읽고 TASK.md를 생성해줘.
각 TASK는 30분~2시간 안에 완료 가능한 단위로 쪼개줘.
완료 조건은 pytest 테스트로 검증 가능하도록 작성해줘.
```

3. 생성된 `TASK.md` 검토

### TASK.md 품질 검증 체크리스트

```
[ ] 모든 PRD 기능이 TASK로 변환되었는가?
[ ] 각 TASK의 완료 조건이 구체적인가? ("잘 작동한다" X, "ValueError 발생" O)
[ ] 너무 큰 TASK(3시간 이상)가 없는가?
[ ] 의존 관계가 최소화되었는가? (병렬 실행 가능성 확인)
[ ] 예상 테스트명이 명시되었는가?
```

---

## 구성 이유

PRD만 있으면 Copilot Agent가 "어디서부터 시작할지" 판단하기 어렵습니다. TASK 단위로 분해해야 AI에게 원자적 작업을 위임할 수 있고, 진행 상황 추적도 가능해집니다. Skills 체이닝의 첫 사례로 적합합니다.
